MIGRATION MISSION

AdventureWorks → Snowflake

Migrations are never just code conversion. Every one forces hard decisions: future-state architecture, preserving history, choosing between big-bang and incremental cutover, and scoping what to carry forward. But most of the effort is validation — proving row counts match, checksums agree, dashboards show the same numbers, and SCD histories have no gaps or overlaps. This mission automated the full journey and its validation — from SSIS packages and Power BI dashboards to Snowflake-native Streamlit and managed notebooks — in a single 7-hour Droid Mission run.

Mission Overview

What we set out to do and what the migration covered.

☁

Source Stack

Microsoft AdventureWorksDW2022 running in Docker SQL Server on localhost:1433. ETL pipelines in T-SQL + SSIS packages. Power BI sales dashboard for analytics.

❄

Target Stack

Snowflake cloud data warehouse with ADVENTUREWORKS_MIGRATED database. Three schemas: STAGING, DW, and UTILITY. Snowpark Notebooks as the primary ETL primitive.

⚙

Migration Strategy

Subset-data migration scope. Code generation first, then live data extraction via pymssql to Parquet, upload to Snowflake internal stage, and load via COPY INTO + MERGE with SCD Type 2 tracking.

📈

Dashboard Migration

Dual approach: generated a Power BI repointing guide and a brand-new Streamlit dashboard deployed as Snowflake Native Streamlit (SiS), styled with Factory AI visual identity — dark base, warm orange accent, Geist typography.

Mission Timeline

Milestone Breakdown

M1
~30 min

Discovery & Assessment

Parsed ETL and dashboard repositories. Built an object inventory of 48 migration objects with complexity scoring (23 Simple / 16 Medium / 9 Complex). Identified all artifact types: T-SQL scripts, SSIS packages, Power BI .pbix, CSV tables. Produced 01-assessment-report.md. 4/4 assertions passed.

M2
~30 min

Target Architecture Design

Designed three-schema target layout: STAGING (raw), DW (star schema with SCD Type 2 columns _valid_from, _valid_to, _is_current), and UTILITY (procs, UDFs, validation). Mapped all 48+ source objects to Snowpark Notebook primitives. Documented SQL Server → Snowflake type mappings. 5/5 assertions passed.

M3
~45 min

DDL & Code Generation

Generated 5 ordered DDL scripts creating database, 31 staging tables, 28 DW tables, file formats, and internal stages. Plus UDFs, a deployment manifest, and connection templates. All scripts executed against live Snowflake with 0 compilation errors. 4/4 assertions passed.

M4
~60 min

Snowpark Notebooks

Generated 3 Python notebooks: SCD Type 2 MERGE logic, data quality checks (row counts, nulls, duplicates), and staging load workflows. Also created a scheduled Snowflake Task TASK_RUN_NB_DATA_QUALITY_DAILY with cron 0 2 * * * UTC, left in SUSPENDED state. All cells executed via jupyter nbconvert --execute. 4/4 assertions passed.

M5
~90 min

Data Migration

Extracted all 31 tables from Docker SQL Server using extract_data.py (pymssql) into Parquet files — 1,060,820 total rows. Uploaded to Snowflake internal stage via PUT. Loaded staging tables with COPY INTO, then populated DW via MERGE with SCD Type 2 logic. Fixed binary-column Parquet load issues by setting BINARY_AS_TEXT=FALSE. 7/7 assertions passed.

M6
~60 min

Dashboard Migration

Generated a Power BI → Snowflake repointing guide with connection-string changes and DAX rewrites. Built a new Streamlit dashboard with Factory AI styling (dark base #0A0A0A, orange accent #FF6B35, Geist font). Six visualizations querying live Snowflake: KPIs, sales trend, top products, geographic map, customer segments, and SCD Type 2 history explorer. Verified via agent-browser screenshots. 6/6 assertions passed.

M7
~45 min

Validation & Packaging

Full validation suite: schema (67/67 objects), row counts (0.00% diff), checksums (all scopes PASS), SCD Type 2 integrity (102/102 checks). Streamlit dashboard verified with real migrated data. Packaged everything into adventureworks-snowflake-deliverable.zip (941 KB). 9/9 assertions passed.

08

Mission Execution Notes

How the mission ran, how it was validated, and what made it different.

One-Shot Mission

This was a single Droid mission that ran end-to-end in approximately 7 hours. It was not split across sessions. Every phase generated artifacts, was validated by automated reviewers, and had to pass before proceeding.

Upfront Validation Contracts

Before any code was written, the mission generated features.json and validation-contract.md with 40 predefined assertions. Each feature had a fulfills array binding it to specific VAL-xxx contracts. Validation was built into the mission structure, not an afterthought.

Scrutiny & User-Testing Validators

After every feature, the orchestrator spawned two validators:

  • scrutiny-validator — automated code review (tests, type checks, linting)
  • user-testing-flow-validator — contract-surface verification

When validators rejected outputs, the mission received pushback and had to fix issues before the milestone was sealed. This happened multiple times across the 7 milestones.

Sealed Milestones

Each of the 7 milestones was sealed only after both its feature artifacts and its validators returned PASS. No milestone could be skipped or short-circuited.
